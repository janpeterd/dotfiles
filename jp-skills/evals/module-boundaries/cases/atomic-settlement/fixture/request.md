The journal is the service's authoritative account balance and accepted-transfer record. `settle` is an existing public operation. Account names and transfer ids are opaque strings. Owner replacement fences old messages, including exact retries of receipts accepted by the prior owner. Invalid requests raise ValueError without changing balances or accepted receipts.

Add `settle_many(receipts) -> tuple[Receipt, ...]` for the batch endpoint. Consume the iterable in input order. Each new receipt observes the preceding balances in that batch. Exact repeats return the accepted receipt and do not debit twice; an id reused with different content is invalid. The whole request is atomic, including generator errors. Empty input succeeds with an empty tuple. Existing single-settlement behavior stays supported. No durable queue, threads or new dependencies are required by the endpoint.
