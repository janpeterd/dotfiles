The job service receives result and cancellation requests sequentially on one event-loop thread. Whichever terminal transition is accepted first wins. A repeat of the same accepted result or cancellation is idempotent. A conflicting result for a successful job raises ValueError. A late result after cancellation is ignored and returns None; cancellation after success returns "succeeded" without sending a cancellation message. Inspect and notification history must agree. There is no durable storage or cross-process recovery requirement in this component.

The team recently separated result and cancellation handling so each file could be smaller. Both handlers still receive the same Job objects. Users now report a successful job switching to cancelled after they already received its result. Review the current design and propose a repair. Preserve the service's caller-facing methods and accepted-result retry behavior. We want a plan with interface and transition sketches, not edits.
