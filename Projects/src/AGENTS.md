# Development conventions for `~/Projects/src`

These conventions apply to every repository below this directory. A repository's own `AGENTS.md` may add project-specific requirements, but must not weaken the secret-handling rules here.

## Repository and branch layout

- Source repositories live under `~/Projects/src`.
- JPSERV repositories live under `~/Projects/src/jpserv`.
- Keep the primary checkout on its normal primary branch (`dev`, `develop`, `main`, or `master`).
- Linked worktrees belong only at `<repo>/.worktrees/<slug>`.
- Never create worktrees below `instances/`, `worktrees/`, `/tmp`, or a path containing `<repo>:<branch>`.
- Use `jp worktree add <name> [--branch <branch>] [--start <ref>]`, `jp worktree list`, and `jp worktree remove <name>` instead of calling `git worktree` directly.

## Secrets and environment files

- Never commit live `.env`, `.env.*`, or `.envrc` files. Template files such as `.env.example` remain versioned.
- Canonical live files are stored with mode `0600` below `~/.config/jpserv/env/<repository>/<scope>/` and symlinked into checkouts.
- `scope` is `root` for the primary checkout or the worktree slug for a linked worktree.
- Use `jp env centralize` after introducing a new local environment file. Do not copy secret values into documentation, logs, issue comments, shell commands, or agent output.
- Do not place secrets in chezmoi. Do not inspect or print secret values unless the user explicitly requests a specific value.
- Do not run `direnv allow` automatically. The user must approve each checkout's `.envrc`.

## Standard commands

Inspect `just --list` before working. Repositories with a runnable application should expose these recipes when applicable:

- `just setup`: idempotently install/fetch dependencies.
- `just dev`: idempotently start the complete local development stack.
- `just test`: run the relevant test suites.
- `just check`: run formatting checks, linting, type checks, and tests appropriate to the repository.
- `just clean`: remove generated build output only; never delete source, secrets, database volumes, or external state.
- `just worktree-add <name>` / `just worktree-rm <name>`: adapters for the `jp worktree` helper.

`just dev` uses the developer-takeover policy through `jp dev`: it may stop Docker containers publishing declared development ports and may TERM, then KILL, listeners owned by the current user. It must refuse non-user/system listeners and must never invoke `sudo`. It must print what it stops.

## State, dependencies, and builds

- Mutable runtime state belongs under `~/Projects/state/<repository>/<scope>`, available as `JP_STATE_ROOT` and through `jp state path`.
- Keep databases, uploads, logs, process metadata, generated certificates, and runtime artifacts outside Git worktrees whenever project tooling supports it.
- Never commit or migrate `node_modules`, `target`, `dist`, `build`, `.venv`, caches, runtime data, or generated bytecode.
- Lockfiles are source and should remain committed.
- Use Nub (`nub`/`nubx`) for JavaScript package execution and installation. Nub handles JavaScript runtime/package versions.
- Use rustup and repository Rust toolchain files for Rust versions. Do not introduce `mise`, asdf, or duplicate version managers.

## Git and safety

- Fetch with pruning, use fast-forward-only pulls, and let pushes establish upstream branches automatically.
- Forgejo HTTPS credentials are stored with the `forgejo-systemd` Git helper in a user-scoped systemd encrypted credential. Never replace it with a URL-embedded token or plaintext credential store.
- Before committing, verify staged paths contain no live environment files, credentials, dependencies, builds, caches, or runtime state.
- Do not force-push, rewrite history, delete worktrees with changes, remove database volumes, or stop system processes without explicit user approval.
- Prefer small repository-specific commits and push them to Forgejo after verification.
